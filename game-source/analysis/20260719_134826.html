结论

新版游戏源码已经修复上一版的高鱼竿实际结算错误：完整 16 槽概率会在抽样前归并到地图稀有度上限，扩展槽不再回退为 N。S1 猫猫乐园的普通表上限也由 UTR 改为 UR，不再自然产出 UTR。

当前利润网仍按 20260717 版实际引擎建模，因此这两项现在反而成为新的高影响不一致：

  • 普通 UR 图在 d=11 时，利润网仍给出 N 7.04%；新版源码为 N 0%、UR 89.15%。

  • 普通 UR 图在 d>=17 时，利润网仍为 N 100%；新版源码为 UR 100%。

  • S1 在 d=9 时，利润网仍给普通表 UTR 11.37%；新版源码普通表 UTR 为 0%，该质量并入 UR。

  • 利润网仍按旧版“原始槽先流星、再运行时映射”处理；新版实际结算已改为“先按地图上限归并、再流星”。

旧报告中用户点名的其他规则大体仍与实际结算一致，包括 11-20 图成就后常驻特殊 UTR、幸运取优、幸运与保底顺序、多多与逗猫棒数量、猫猫乐园鱼价取整、猫天气和礼物规则。需要注意，概率封顶发生在幸运双抽之前，利润网保留“封顶前稀有度”作为取优优先级的做法也已经过时。

新版还取消了展示木框和猫猫框出售。展示木框按 0 计价现在与“无直接出售收入”一致；猫猫框 200 不再是源码售价，只能视为用户指定估值。

源码自身仍有问题：实际流星路径在 d>=12 会形成 N=-2% / UR=102% 的内部数组；状态页流星展示仍走旧的 raw-first 路径，并可能在普通 UR 图展示不可能由普通表产出的 UTR。本文以实际结算路径为利润网对齐口径，同时单独记录这些源码展示、文档和实际执行的不一致。

新版实际结算调用链

一次捕获的关键顺序如下：

  1. FishingBuffCalculator.get_effects_at_time 计算有效鱼竿、鱼饵、天气和药水；多多令有效鱼竿减 1，见 models/buff.py:463 和 models/buff.py:511。

  2. 11-20 图未完成 collect_scene_<id> 时把运行时上限压到 UR；完成后保留配置中的 UTR，见 engine.py:1009。

  3. S1 加载材料率、逗猫棒、城堡、鱼饵节省和过山车天气增幅，见 engine.py:1016。

  4. 水晶猫城堡每次捕获只判定一次鱼竿 +1；幸运药水两个随机结果共用该等级，见 engine.py:525。

  5. 先计算多多/逗猫棒数量，再依次检查展示木框保底、特殊 UTR 保底；触发保底时跳过幸运双抽，见 engine.py:380 和 engine.py:400。

  6. 未触发保底时，每个随机结果依次判定 S1 材料、非星空图 0.7% 展示木框、特殊 UTR、普通稀有度表，见 engine.py:176。

  7. 普通稀有度表先归并到地图上限，再应用流星，最后抽样，见 engine.py:214。

  8. 幸运从两个完整随机结果中取优，随后只按最终结果更新一次保底，见 engine.py:439 和 engine.py:481。

仍保留的差异

旧报告列出的 13 项未点名差异在新版中都仍存在；本轮没有修改利润网。

1. 24 小时尾段仍向下取整

游戏对不足一个完整间隔的尾段按 remaining / interval 再做一次 Bernoulli 捕获：engine.py:801。利润网仍用 floor(24 / interval)：[app.js:2672](/home/luyh7/game/fishing-profit/app.js:2672)。因此最多漏掉不足 1 次鱼获及对应成本。

2. 地图准入道具未建模

游戏中 S1 需要门票但不再检查杆级；11-20 图需要星空艇并检查杆级：actions.py:171。利润网只按原始鱼竿与难度过滤：[app.js:2714](/home/luyh7/game/fishing-profit/app.js:2714)。

3. 库存、换饵与逐时状态未模拟

游戏按结算时间点重新计算 buff，并在鱼饵耗尽后切换到库存中价格最高的鱼饵，最终进入无饵模式：engine.py:950、engine.py:981。利润网把当前状态外推 24 小时并假设候选鱼饵无限。

4. 其他药水和 buff 未计入

游戏仍支持许愿、加速、双倍捕获、闪光等效果；利润网配置只提供无药水、多多和幸运：[config.js:47](/home/luyh7/game/fishing-profit/config.js:47)。这些效果会改变速度、数量或额外奖励。

5. 星空鱼和星空天气额外奖励未计入

新版星空鱼掉率为：

5% + max(0, effectiveRodLevel - 10) * 0.5% + (solarWind ? 2.5% : 0)

各项是绝对百分点相加，见 starry_system.py:543；实际捕获会传入有效鱼竿并生成奖励：engine.py:600。幸运和流星雨会增加候选编号，多多会复制同号星空鱼，新版还增加对子/葫芦评分和碎片奖池。利润网仍完全没有折算这些收益。

6. 首条 UTR 消耗和一次性成就收益未计入

第一条未收集 UTR 会被自动消耗以解锁图鉴，不进入可出售背包；其余数量才入包：result.py:60。利润网把所有 UTR 都按可售鱼计入稳态收益，也不计一次性成就金币。

7. 猫礼物的同稀有度选鱼策略不同

源码优先鱼池中的第一条未收集鱼，全部收集后才选最贵鱼：cat.py:67。利润网未完成场景成就时仍使用同稀有度随机鱼平均值，完成后才使用最贵鱼：[app.js:2590](/home/luyh7/game/fishing-profit/app.js:2590)。

8. 猫猫框 15 次保底未建模

源码在每次猫吃鱼时推进猫框计数，达到 15 次直接给框：cat.py:25。利润网只计算 15% 随机猫框及幸运额外判定：[catch-outcome.js:815](/home/luyh7/game/fishing-profit/catch-outcome.js:815)。

9. 手动猫猫乐园建筑可形成非法组合

源码用传奇猫雕像等级门控其他建筑升级：cat_park.py:257。利润网页面只在升级雕像本身时检查其他八栋建筑，并允许手动降级：[app.js:4729](/home/luyh7/game/fishing-profit/app.js:4729)、[app.js:5644](/home/luyh7/game/fishing-profit/app.js:5644)。自动同步的真实玩家状态不受影响。

10. 页面使用长期保底稳态，不读取当前计数

状态 API 的玩家负载仍未提供 frame_pity_counter、utr_pity_counter 或 cat_frame_pity_counter：status_api.py:502。利润网继续用长期稳态 Markov 分布：[catch-outcome.js:597](/home/luyh7/game/fishing-profit/catch-outcome.js:597)。临近保底玩家的短期结果会不同。

11. 幸运与水晶猫城堡的相关性不同

游戏每次捕获只判一次城堡，然后幸运两次随机结果共用鱼竿等级：engine.py:525。利润网先混合“基础等级/等级+1”两档分布，再做独立幸运取优：[app.js:2428](/home/luyh7/game/fishing-profit/app.js:2428)。

12. 手动模式没有星空成就输入

星空特殊 UTR 只从自动玩家快照的 achievements 判断：[app.js:831](/home/luyh7/game/fishing-profit/app.js:831)、[app.js:3566](/home/luyh7/game/fishing-profit/app.js:3566)。未匹配玩家无法手动声明各星空图已完成成就，当前会按未解锁处理。

13. 过山车天气增幅未作用于迷途风 UTR

游戏会把过山车增幅写入 weather_lost_wind_multiplier：engine.py:1036。利润网特殊 UTR 只混合城堡的鱼竿等级，没有乘天气增幅：[app.js:843](/home/luyh7/game/fishing-profit/app.js:843)。

14. 手动迷途风可绕过普通图成就门槛

游戏会在加载 buff 时过滤未完成场景成就玩家的迷途风：models/buff.py:241。利润网手动天气覆盖在成就门控之前直接返回：[app.js:680](/home/luyh7/game/fishing-profit/app.js:680)，而非星空图的特殊 UTR 开关不检查 hasAchievement：[catch-outcome.js:849](/home/luyh7/game/fishing-profit/catch-outcome.js:849)。因此手动选择迷途风时，1-10/S1 即使未完成 collect_scene_<id> 也会计算 UTR。

用户指定和有意差异

  • 展示木框价值固定为 0。新版已删除其出售入口，直接现金价值同为 0；框仍可用于速度 buff 和升级展示栏位，这部分非现金用途未估值。源码说明见 doc.md:191。

  • 猫猫框价值固定为 200。新版同样不可出售，源码没有固定现金等价；利润网的 200 是用户指定估值，不是新版源码售价。

2. 流星展示仍使用旧的 raw-first 路径

calculate_display_probabilities 先正确计算带上限、带多多的分布，但有流星时会把结果整个替换为原始槽计算：probability.py:31。get_meteor_adjusted_probabilities 在 raw 16 槽上先流星，再把 index 5 及以上汇总为 UTR，且普通 UR 图不重新封顶：constants.py:291。

图1 Lv.11、d=11、流星 +2%：

  • 实际结算：SSR 8.85% / UR 91.15%。

  • 源码状态页：SSR 10.85% / UR 44.26% / UTR 44.89%。

状态页会展示普通概率表不可能产出的 UTR。该替换还丢掉 duoduo_count 数量倍率：无流星时多多展示总和为 200%，有流星后回到 100%。

3. 过山车 UTR 增幅没有进入源码概率展示

实际结算会放大迷途风特殊 UTR：engine.py:1036。展示函数只有 weather_lost_wind: bool，没有 multiplier 参数：probability.py:12。例如 S1 Lv.15、过山车 Lv.3，实际条件概率为 1.1%，展示仍为 1.0%。

4. 保底触发提示有一位偏差

真实保底条件为 (pity + 1) >= 150：engine.py:403、engine.py:411。主循环调用前却用 pity >= 150 标记本次是否保底：engine.py:1169。计数为 149 时奖励会正确触发，但不会追加“保底触发”消息；奖励结算本身不受影响。
