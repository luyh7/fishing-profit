源码问题游戏源码 Bug

1. 跨 23:00 的结算会按错误天气日判定乱纪元，并把结果覆盖整个区间（高）

is_chaotic_era_active()虽接收 at_time，查询天气记录时却固定使用当前 weatherdate()。preparefishing_context()又只以 settle_start 判定一次，并将迷途风 Buff 覆盖整个待结算区间。

因此 22:50-23:10 一类跨天气日结算既可能找不到旧天气记录，也可能将新天气误用于 23:00 前的鱼获；乱纪元实际启用的特殊 UTR 与 150 次保底会漏算或多算。状态查询和收杆均走这条路径，故不是单纯展示问题。

2. 结算路径违反自身的原子性承诺（高）

收杆声明事务外阶段只读、失败后数据库保持收杆前状态，但它先在事务外调用 computesettle_step()。模拟内部的switchdepleted_bait()会直接保存 user.bait_id，这次写入不在随后收杆事务中，后续失败无法回滚。

状态查询路径也先保存结算状态，再单独扣除鱼饵。两次写入之间若失败，鱼获、保底和最后结算时间已推进，鱼饵却未扣除，违反会话状态与成本应一致提交的要求。

3. 并发的状态查询与收杆可用过期快照覆盖已结算鱼获（高）

computesettle_step()在没有锁的情况下读取会话快照并计算 updated_status。状态查询可立即写入该快照，而收杆直到事务内部才锁用户，且没有比较 last_settle_time 或版本号。

例如收杆 A 与查询 B 都从 S0 计算，B 先将 SB 写入并扣饵，A 随后持有锁仍把基于 S0 的 SA 应用为最终收杆结果。B 那段鱼获、保底、猫礼物和最后结算时间会丢失，而 B 的鱼饵已经扣除；同一会话的收益和成本因此不一致。

4. 钓鱼期间“设定鱼饵”会追溯改写尚未结算时间段（中）

结算上下文的注释明确约定钓鱼期间设定只改 preferred_bait_id，当前 bait_id 应保持到下一次开钓（core/actions.py，玩法文档）。实际的set_preferred_bait()同时写入两者。

下一次状态查询或收杆会依当前 bait_id 对从旧 last_settle_time 起的整段时间重新模拟，导致中途换饵者以新鱼饵的速度、概率与成本结算已经过去的时段。这与源码承诺相矛盾，且会直接改变鱼获数量、稀有度和鱼饵消耗。

5. 实际捕获与游戏内概率展示对特殊 UTR 的门控相互矛盾（高）

捕获引擎仅在 weather_lost_wind=True 时启用星空特殊 UTR 和其保底；结算上下文也只在已解锁且乱纪元有效时才注入该 Buff。相反，展示概率函数把 starry_utr_unlocked 与迷途风作“或”判断，状态页完成成就后无条件传入该标记（调用处）。

这会在太阳风、流星雨、恒纪元以及非生效乱纪元中显示非零 UTR 概率，但实际掉落率为零；玩家据此选择地图或判断保底状态会被误导。

6. 累计达到 1200 分不会实际发放 S2 入场券（高）

s2_ticket_claimed在目标源码中只有定义和读取。流星鱼结算会累加积分，收杆则仅构造 reached/claimed 展示信息，不存在将该字段写为已领取或发券的业务路径。

帮助页仍承诺 1200 分“可获得”入场券（help.html）。因此玩家可达到阈值却无法获得承诺的解锁结果。

7. 黑商将锁定 UTR 换成首条目标 UTR 时，目标会被消耗却被谎称“已自动锁定”（中）

黑商先移除锁定来源，再调用add_fish_to_user()，随后不检查锁定操作的返回值便追加“已自动锁定”。若目标是未收集的 UTR，入库逻辑会只解锁图鉴并自动消耗该鱼，不创建背包条目；toggle_lock_by_numeric_id()此时返回 False。

这违反同次提交新增的维护约束“锁定来源的实际获得鱼应留在背包并继承锁定”（AI_MAINTENANCE.md）。锁定来源被消耗后，玩家既没有可锁定的目标鱼，也收到错误结果提示。

8. 第 150 次保底奖励正确，但触发提示晚一轮（低）

实际保底使用 (pity + 1) >= 150，提示预判却使用 pity >= 150。计数为 149 时，第 150 次鱼获已被强制保底但不会显示对应提示；UTR 与木框两类提示均受影响。

9. 玩家帮助仍描述已废止的星空规则（中）

doc.md仍称乱纪元无效果、成就后的 UTR 常驻，且在木框章节引用已不存在的 STAR_FRAMES_MAX；网页帮助也保留“乱纪元无效果”的说法（help.html）。

这些说明与实际结算的乱纪元门控及当前无星辰木框上限的实现冲突，会误导玩家规划天气、保底与木框资源。

收益问题利润网 Bug

1. 星空特殊 UTR 被按完成成就后全天启用，实际只在有效乱纪元启用（高）

利润网的isSpecialUtrEnabled()对星空地图只检查场景成就，忽略传入的天气类型与 weatherInactive；app.js虽传入天气状态，结果没有参与判断。该结果进入捕获分布与 150 次保底，直接影响鱼价期望和 netRevenue。

目标源码的实际结算只有在已解锁且乱纪元有效时才注入迷途风 Buff（core/actions.py），引擎再以该 Buff 启用特殊 UTR（core/engine.py）。因此利润网将太阳风、流星雨、恒纪元以及未生效乱纪元中的 UTR 随机收益和保底推进错误计入；现有回归测试还把太阳风下的错误行为固定为预期。

2. 缺失或非法的星空天气被利润网伪造为“生效中的乱纪元”（中）

getWeatherForMap()在缺失源天气时先构造晴天，在类型不被星空天气集合接受时改为 chaotic_era，并同时强制写入 is_active: true、清空起止时间。目标源码遇到无天气记录时虽为便于显示返回 chaotic_era，但明确返回 is_active: False，其他未解锁或结束的星空占位显示也保持非生效（weather_service.py）。

这把仅用于展示的占位天气当作真实效果状态。当前它被“全天特殊 UTR”问题掩盖；即使修正上一项，缺失或非法天气仍会继续错误地启用特殊收益与保底。

3. 有效的 double_catch 被普通钓鱼收益链漏算（高）

页面能识别玩家当前生效的 double_catch Buff（app.js），但该状态只传给独立的星空期望模块（app.js）；普通地图的数量与收益计算仅考虑多多和猫乐园分支（app.js）。

目标源码会将 double_catch 转为实时 Buff（models/buff.py），并在所有地图的每个钓鱼间隔执行两次捕获（S1 材料分支例外）（core/engine.py），一枚鱼饵仍按整个间隔后置扣除（core/engine.py）。所以 Buff 生效期间页面低估鱼获价值、grossRevenue 与 netRevenue。

4. 星空评分 PMF 仍按旧规则生成，积分、奖池和奖励期望已漂移（高）

目标源码的滑梯与回文规则允许全同号同时命中两类番型。利润网的 JavaScript 移植仍要求滑梯至少移动一次并排除全同号回文（generate-starry-score-pmf.js）。例如目标规则下 777777 的原始分为 15.047072、进入究极池（目标测试），利润网旧移植则为 8.705465、仅高级池。

生成器固定的源码指纹仍是旧值（generate-starry-score-pmf.js），检入 PMF 因而保持旧分布：普通域单候选平均原始分从 0.797450768 增至 0.840278102，究极池概率从 0.0574% 增至 0.0844%；恒纪元分别从 1.433352226 增至 1.514901110、0.2651956% 增至 0.3748438%。starry-expectation.js据该 PMF 计算积分、奖池抽取和奖励期望，所以星空区域展示的这些数值均不再对应目标游戏。根据 PRD 的既定口径，这部分不计入 netRevenue，但仍是已承诺的独立星空期望功能错误。

待定差异源码与利润网有差异但无法确定是否为 Bug

1. 收杆尾数是否应按源码的概率保留，还是按页面的整次向下取整

源码会按剩余时间占一个间隔的比例再做一次捕获判定（core/engine.py；core/engine.py），页面则以整次完成数向下取整（app.js）。

这会影响任意不足一个完整钓鱼间隔的长期期望，但 PRD 已明确采用向下取整口径。需要用户决定利润网要严格复现单次收杆分布，还是保留当前更保守的产品口径。

2. 无上限星辰木框与自动奇迹消费是否需要计入长期利润

目标源码不再设置星辰木框持有上限（core/starry_system.py），并会在收杆时自动寻找并消耗可组成奇迹的流星鱼。星空木框升级最多 10 个，满级后继续产生星辰木框及自动消耗流星鱼的长期价值没有统一的鱼币定义。

利润网目前不为流星鱼、奇迹或星辰木框折算鱼币。是否要把它们的机会成本或后续收益纳入利润，取决于产品要把这些非直接出售资源定义为净利润的一部分，还是继续仅显示其独立期望；这一估值口径需要用户决定。
