## 游戏源码 Bug

### 1. 并发结算仍会按过期会话快照重复扣饵并覆盖鱼获（高）

[_compute_settle_step()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/actions.py#L255-L321) 在无锁条件下读取会话并模拟完整结果；[状态查询路径](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/actions.py#L335-L353) 计算完成后才进事务，既不锁用户行也不比较 `last_settle_time`。收杆同样在事务外完成模拟，事务内的[行锁](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/actions.py#L920-L940)只检查会话是否仍存在，再直接应用先前基于旧快照的 `updated_status` 与 `bait_usage`。

两个状态查询可从同一 S0 生成结果，后写者覆盖鱼获、保底和时间推进，但两边都按各自 `bait_usage` 扣饵；状态查询与收杆并发时，收杆还会把基于 S0 的计划套到已推进的用户状态。事务只保证单次写入同成同败，不能保证计划对应当前快照，收益、成本和状态均可能重复或丢失。

### 2. 卖鱼和卖饵仍不是原子交换（高）

[sell_fish()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/backpack/sell.py#L20-L49) 按可售快照计价后，依次删库存、加金币和加次数；[delete_fish_entries()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/models/user.py#L795-L803) 没有行锁也不返回实际删除数量，[add_gold()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/models/user.py#L366-L373) 是无锁读改写。[sell_bait()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/backpack/sell.py#L154-L185) 也忽略 `remove_item()` 的布尔返回值后直接加币。

并发出售可同时按同一库存报价，后执行者即使没有删到对应物品仍会发币；删除后加币失败又会让物品消失而未结算款项。出售是收益闭环的最终兑现步骤，库存与金币必须在同一锁定事务内提交。

### 3. 钓鱼中设定优先鱼饵会追溯改写未结算区间（中）

结算上下文明确约定钓鱼期间只修改 `preferred_bait_id`，当前 `bait_id` 应保持到耗尽后由模拟切换，[证据见这里](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/actions.py#L116-L120)。但 [set_preferred_bait()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/bait.py#L43-L63) 同时写入两个字段。

下一次状态查询或收杆会用新 `bait_id` 从旧的 `last_settle_time` 模拟整段历史，设定前已经过去的时间会按新鱼饵的速度、概率和成本结算。这与自身会话语义相矛盾，并直接改变实际鱼获和鱼饵消耗。

### 4. 有鱼饵消耗的步进结算仍会强制切到最贵鱼饵（中）

模拟器只在当前鱼饵耗尽时才选择价格最高的备用饵；目标版本还把步进结算的自动换饵声明为临时结果，收杆才统一落库，[见 settle_fishing_step 注释](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/actions.py#L343-L353)。但状态结算的 [consume_bait_incremental()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/bait.py#L66-L87) 和收杆事务内的[对应实现](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/models/user_mutations.py#L624-L646) 在扣除任意一枚鱼饵后均无条件选择最贵库存鱼饵并覆盖 `bait_id`。

因此当前鱼饵仍有库存时，只要发生一次带扣饵的状态结算，持久化 `bait_id` 就会被改成更贵、速度不同的鱼饵。它既绕过“步进不持久化临时换饵”的新设计，也偏离模拟器“耗尽后换饵”规则，后续收益和成本都会漂移。

### 5. 跨鱼饵的猫礼物被合并成一种鱼饵发放（中）

捕获循环将当时的 `bait_id` 传给猫礼物逻辑；[process_cat_gift()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/cat.py#L44-L51) 只保存第一种非空 ID，却累加之后所有 `bait_count`。跨状态合并时，[merge_cat_gifts()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/cat_gift.py#L29-L46) 又可能以新 ID 覆盖旧 ID 并继续累加数量。

一次猫天气会话若跨越自动换饵，最终只会发放一种鱼饵，数量却来自多种饵的礼物判定。入库礼物与真实捕获路径不一致，影响成本补偿和收益。

### 6. 幸运药水的商店时长与实际时长相差四小时（中）

[shop.json](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/config/shop.json#L129-L136) 配置并展示幸运药水持续 720 分钟、即 12 小时；[use_lucky_potion()](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/shop/potion_use.py#L137-L190) 却硬编码每瓶只加 8 小时。

玩家按商店信息使用后少获得四小时效果，多瓶叠加时误差线性扩大。运行路径、配置和展示不能同时成立，直接影响有效收益时间。

## 利润网 Bug

### 1. 有效的 `double_catch` 仍被普通钓鱼收益链漏算（高）

页面仅将 `doubleCatch` 传给星空期望，[见星空调用](../../app.js#L5229)；普通地图的[每日次数与收益计算](../../app.js#L3010-L3114) 只使用药水数量倍率和猫乐园额外数量，未纳入该 Buff。目标源码会在每个间隔将 `base_catch_count` 设为 2 并执行两次基础捕获，[实际循环](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/engine.py#L694-L729)，整组仍只进行一次鱼饵消耗记录。

因此 `double_catch` 生效时，普通图鱼获价值、`grossRevenue` 和 `netRevenue` 都被低估，而成本不应同比翻倍；这也违背了利润网自身 PRD 对该 Buff 的承诺。

### 2. 星空积分 PMF 仍锁定旧评分器，未覆盖目标的对子改写与既有新番型（高）

[生成器](../../scripts/generate-starry-score-pmf.js#L14-L17) 和[检入产物](../../starry-score-pmf.js#L2852) 仍记录旧 `starry_system.py` 指纹 `0d0c39fd...`，目标文件 SHA-256 已变为 `a1045283...`。本增量将对子规则改为相邻 run 判定，并把 `two_pair` 权重从 `1.359121` 调整为 `1.595508`，[规则定义](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/starry_system.py#L145-L146) 与[实际检测](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/starry_system.py#L292-L332) 均已改变；生成器仍按“长度恰好为 2 的 run 计数”和旧权重打分。既有全奇/全偶、严格兜底屁胡等规则也仍未移植。

页面的流星鱼原始分、奖池概率、碎片连锁和奖励积分仍基于旧 PMF，目标源码实际结算会逐条评分并发放对应奖池奖励，因此所有这些星空期望都会漂移。利润网 `生成器可重复生成当前检入产物` 测试已因指纹不一致失败。

### 3. 伽马射线暴漏掉流星鱼最终掉率翻倍（高）

[starry-expectation.js](../../starry-expectation.js#L288-L301) 将伽马映射为三类天气，但其掉率公式只加入太阳风的 `+2.5%`，没有乘以 2。目标源码在基础、鱼竿和太阳风加成合计后，对伽马[执行 `drop_rate *= 2` 并封顶](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/starry_system.py#L648-L666)。

闪光药水期间，页面低估流星鱼数量、积分、各奖池抽取次数及其奖励期望。

### 4. 中级奖池的猫框数量少算为 1 个（中）

[利润网奖池定义](../../starry-expectation.js#L75) 把中级池猫框设为 1 个；目标源码的[同一奖池项](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/starry_system.py#L34-L57) 实际发放 3 个。

页面的奖池展示和猫框期望都只有真实值的三分之一，进一步影响以猫框为输入的资源判断。

### 5. 自动打窝同步忽略星空图 `cat_nest`（中）

目标源码为星空图增加独立的猫框打窝层，并按 `+5%` 计入总速度，[见 scene 汇总](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/scene.py#L97-L107)。状态接口按 buff 类型原样计数，会在 `locations[].buffs` 中输出 `cat_nest`，[见批量统计](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/status_api.py#L306-L322)。

利润网自动打窝仍只累加 `nest + frame + starry_bonus`，[见 app.js](../../app.js#L2450-L2454)，PRD 也只写了这三项。星空图存在猫框打窝时，页面速度、完成次数和收益都会系统性偏低。

## 源码与利润网有差异但无法确定是否为 Bug

### 1. 伽马与多多/幸运应只展示可达组合，还是保留组合假设分析

利润网的 PRD 明确允许伽马与主药水共存，页面也可同时把这些状态传给星空期望；目标源码则把真多多、幸运和闪光药水列为互斥组，[证据见这里](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/shop/potion_use.py#L18-L34)。

若产品目标是复现玩家可达的真实结算状态，应改为三选一；若页面有意用于理论组合比较，则应保留计算并由用户确认该非真实状态的产品口径。

### 2. 收杆尾数应保留源码概率，还是继续按整次向下取整

利润网利润表以 `floor(24 / interval)` 计算完整捕获次数，[见此处](../../app.js#L2936-L2940)；目标模拟器对不足一个完整间隔的尾段还会按 `remaining / interval` 概率尝试一次捕获，[实际路径](https://github.com/RShock/zhenxun_plugin_fishing/blob/6ba6fce2f55e7c9e57ac8f9cab2fec15c0d76620/core/engine.py#L787-L812)。星空期望已按 PRD 保留尾数贡献，普通利润表则明确选择向下取整。

这会影响任意不足一个完整间隔的长期期望。需要用户决定继续采用保守的“完成周期”口径，还是改为复现单次收杆的概率期望。
