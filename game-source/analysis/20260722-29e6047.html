源码问题游戏源码 Bug

1. 并发结算仍会按过期会话快照重复扣饵并覆盖鱼获（高）

computesettle_step()先读取会话并在无锁条件下模拟完整结果；状态查询路径直到计算完成后才进入事务，既不锁用户行也不比较 last_settle_time。收杆同样在事务外计算，事务内的行锁只检查会话是否仍存在，再直接应用先前的 updated_status。

两个状态查询可从同一 S0 生成结果，后写者覆盖鱼获、保底和时间推进，但两边都按各自 bait_usage 扣除鱼饵；状态查询与收杆并发时，收杆还会把基于 S0 的计划套到已推进的用户状态。事务只保证单次写入同成同败，不能保证计划对应当前快照，收益、成本和状态均可能重复或丢失。

2. 卖鱼和卖饵仍不是原子交换（高）

sell_fish()按可售快照计价后，依次删库存、加金币和加次数；delete_fish_entries()没有行锁也不返回实际删除数量，add_gold()是无锁的读改写。sell_bait()也忽略 remove_item() 的布尔返回值后直接加币。

并发出售可同时按同一库存报价，后执行者即使没有删到对应物品仍会发币；删除后加币失败又会让物品消失而未结算款项。出售是收益闭环的最终兑现步骤，库存与金币必须在同一锁定事务内提交。

3. 钓鱼中设定优先鱼饵会追溯改写未结算区间（中）

结算上下文明确约定钓鱼期间只修改 preferred_bait_id，当前 bait_id 应保持到耗尽后由模拟切换，证据见这里。但 set_preferred_bait()同时写入两个字段。

下一次状态查询或收杆会用新 bait_id 从旧的 last_settle_time 模拟整段历史，设定前已经过去的时间会按新鱼饵的速度、概率和成本结算。这与自身会话语义相矛盾，并直接改变实际鱼获和鱼饵消耗。

4. 每次有鱼饵消耗的结算都会切换至最贵鱼饵（中）

模拟器只在当前鱼饵耗尽时才选择价格最高的备用饵，证据见 switchdepleted_bait()。但状态结算的 consume_bait_incremental()和收杆事务内的对应实现在扣除任意一枚鱼饵后均无条件选择最贵库存鱼饵并覆盖 bait_id。

因此当前鱼饵仍有库存时，只要结算一次，下一段就可能被强制换成更贵、速度不同的鱼饵。它既绕过优先鱼饵语义，也让后续收益和成本偏离本次模拟所承诺的“耗尽后换饵”规则。

5. 跨鱼饵的猫礼物被合并成一种鱼饵发放（中）

捕获循环将当时的 bait_id 传给猫礼物逻辑；process_cat_gift()只保存第一种非空 ID，却累加之后所有 bait_count。跨状态合并时，merge_cat_gifts()又可能以新 ID 覆盖旧 ID，同时继续累加数量；最终发放只能以单个 bait_id入库。

长结算内发生自动换饵，或两次状态结算使用不同鱼饵时，本应按各次当前鱼饵分别获得的礼物会全部变为一种鱼饵。这是已发生事件的物品错误，不是利润网忽略的有限库存模拟差异。

6. 多数量捕获跨过 150 次 UTR 阈值时保底仍会延后一组（中）

UTR 保底检查只以 utr_pity + 1 判断，而普通捕获会按 duoduo_mult 将计数一次增加多次，证据见计数更新。玩法说明承诺每累计 150 次必出 UTR，对应规则。

例如计数为 148 且本组双倍鱼数量为 2 时，检查认为 149 未达到阈值，随后直接写成 150；保底被推迟到下一组而非第 150 次捕获。b273220 只修正了提示预判，未修正实际阈值判定。

7. 黑商交换锁定鱼到首条 UTR 时仍会丢失应继承锁定的目标鱼（中）

黑商逻辑先移除锁定来源，再以统一入库流程加入目标并尝试锁定。首条 UTR 在入库逻辑中被图鉴消耗，随后 toggle_lock_by_numeric_id()找不到背包项而返回 False。维护约束却要求锁定来源的实际获得鱼留在背包并继承锁定，见此处。

目标版本不再错误显示“已自动锁定”，但仍让玩家用锁定来源换取后只得到一次图鉴解锁，既无目标背包鱼也无法继承锁定，仍违反明确的交换承诺。

8. 幸运药水的商店时长与实际时长相差四小时（中）

shop.json配置并展示幸运药水持续 720 分钟、即 12 小时；use_lucky_potion()却硬编码每瓶只加 8 小时。

玩家按商店信息使用后少获得四小时效果，多瓶叠加时误差线性扩大。运行路径、配置和展示不能同时成立，直接影响有效收益时间。

收益问题利润网 Bug

1. 有效的 double_catch 仍被普通钓鱼收益链漏算（高）

页面仅将 doubleCatch 传给星空期望，见星空调用；普通地图的每日次数与收益计算只使用药水数量倍率和猫乐园额外数量，未纳入该 Buff。目标源码会在每个间隔将 base_catch_count 设为 2 并执行两次基础捕获，实际循环，整组仍只进行一次鱼饵消耗记录，证据见这里。

因此 double_catch 生效时，普通图鱼获价值、grossRevenue 和 netRevenue 都被低估，而成本不应同比翻倍；这也违背了利润网自身 PRD 对该 Buff 的承诺。

2. 星空积分 PMF 仍锁定旧评分器，未覆盖目标的新番型（高）

生成器和检入产物仍记录旧 starry_system.py 指纹 0d0c39fd...，目标文件 SHA-256 已变为 4a2a6152...。目标评分器加入全奇/全偶、分块连号和严格兜底的屁胡等规则，规则定义与实际评分均已改变。

页面的流星鱼原始分、奖池概率、碎片连锁和奖励积分仍基于旧 PMF，目标源码实际结算会逐条评分并发放对应奖池奖励，因此所有这些星空期望都会漂移。

3. 伽马射线暴漏掉流星鱼最终掉率翻倍（高）

starry-expectation.js将伽马映射为三类天气，但其掉率公式只加入太阳风的 +2.5%，没有乘以 2。目标源码在基础、鱼竿和太阳风加成合计后，对伽马执行 drop_rate *= 2 并封顶。

闪光药水期间，页面低估流星鱼数量、积分、各奖池抽取次数及其奖励期望；现有测试固化的 0.075 掉率同样是旧规则。

4. 中级奖池的猫猫框数量少算为 1 个（中）

利润网奖池定义把中级池猫猫框设为 1 个；目标源码的同一奖池项实际发放 3 个。

页面的奖池展示和猫猫框期望都只有真实值的三分之一，进一步影响以猫猫框为输入的资源判断。

待定差异源码与利润网有差异但无法确定是否为 Bug

1. 伽马与多多/幸运应只展示可达组合，还是保留组合假设分析

利润网的 PRD 明确允许伽马与主药水共存，见定义，页面也可同时把这些状态传给星空期望；目标源码则把真多多、幸运和闪光药水列为互斥组，证据见这里。

若产品目标是复现玩家可达的真实结算状态，应改为三选一；若页面有意用于理论组合比较，则应保留计算并由用户确认该非真实状态的产品口径。

2. 收杆尾数应保留源码概率，还是继续按整次向下取整

利润网以 floor(24 / interval) 计算完整捕获次数，见此处；目标模拟器对不足一个完整间隔的尾段还会按 remaining / interval 概率尝试一次捕获，实际路径。

这会影响任意不足一个完整间隔的长期期望，但 PRD 已明确选择向下取整。需要用户决定继续采用保守的“完成周期”口径，还是改为复现单次收杆的概率期望。
